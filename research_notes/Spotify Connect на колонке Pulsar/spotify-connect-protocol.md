# Spotify Connect: discovery, transfer, state sync, and third-party device behaviour

*Compiled 2026-10-26. Source labels used below: **[Official]** = Spotify developer/support docs; **[RE]** = reverse-engineered implementation docs (librespot / go-librespot); **[Community]** = user reports or forum posts; **[Inference]** = my reasoning from cited facts, not documented by Spotify. No credentials are reproduced here. Spotify changes this stack without notice; treat all undocumented behaviour as unstable.*

---

## Q1. Why does a Chrome Web Player show up in the Connect list — including under "other networks" — while an arbitrary network audio endpoint does not?

### Takeaway
Spotify Connect has **two independent visibility planes**: (a) link-local mDNS/DNS-SD discovery of a device's ZeroConf HTTP endpoint, and (b) an **account-scoped device registry in Spotify's cloud**. A browser tab can only participate in (b), because a web page cannot advertise `_spotify-connect._tcp` or accept inbound HTTP; therefore it is only ever known as an account device and is bucketed as "other networks". An arbitrary LAN audio endpoint participates in neither plane, so it is invisible.

### Cited Findings
- The Web Playback SDK is explicitly "a client-side only JavaScript library designed to create a **local Spotify Connect device in your browser**" — [Official, Web Playback SDK overview](https://developer.spotify.com/documentation/web-playback-sdk).
- Instantiating `new Spotify.Player({name, getOAuthToken, volume})` and calling `connect()` produces "a new client called … in Spotify Connect"; the `ready` event returns a `device_id`, and `not_ready` means "Device ID has gone offline" — [Official, Web Playback SDK getting started](https://developer.spotify.com/documentation/web-playback-sdk/tutorials/getting-started). This is a cloud-registered player identity, not an mDNS service.
- Spotify's own description of `GET /me/player/devices`: the list "will include any open Web Playback SDK apps, many online Spotify Connect speakers, and Spotify-built apps that you may have open, like the web player" — [Official, Spotify Engineering, "Spotify's Player API" (2022)](https://engineering.atspotify.com/2022/04/spotifys-player-api).
- Hardware visibility requires mDNS + HTTP: the device must advertise `_spotify-connect._tcp` with an `SRV` record (IP/port) and a `TXT` record `CPath=<path>`; the phone then calls `http://<ip>:<port>/<path>?action=getInfo` and "the speaker shows up in the Connect device picker … if it receives a valid reply from the getInfo request" — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf); [Official, Commercial Hardware FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- Account-based fallback is documented: "**If the same user is already logged in both to the speaker and to the mobile app, the speaker will show up even if an error occurs in the ZeroConf discovery**" — [Official, Commercial Hardware FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- Spotify Support: "Try logging into the device using your Spotify credentials and you should be able to see it in the Spotify app **even if it isn't on the same WiFi**" — [Official, Spotify Connect support article](https://support.spotify.com/us/article/spotify-connect/).
- The mobile app has an explicit locality filter: switching **off** "Local device visibility" (Settings → Apps and devices) "lets the app see devices that aren't currently on your WiFi network"; conversely it can be used to show only local devices — [Official, Spotify Connect support article](https://support.spotify.com/us/article/spotify-connect/).
- The web player has a different, narrower view: "you can only use devices **you've already logged into**, or **Google Cast devices on your current network** (if using Chrome)" — [Official, Spotify Connect support article](https://support.spotify.com/us/article/spotify-connect/). Cast is a separate discovery protocol from Spotify's mDNS.
- mDNS is link-local multicast; it does not cross VLANs/subnets without an mDNS reflector, which is why Spotify Connect breaks across segmented networks even when IP routing works — [Community, OpenWrt forum](https://forum.openwrt.org/t/spotify-connect-with-different-vlans-does-not-work-even-with-mdns/169860); [Community, r/Ubiquiti](https://www.reddit.com/r/Ubiquiti/comments/ghdosc/use_spotify_connect_across_vlans/).
- Users repeatedly report devices that are on the **same** Wi-Fi being labelled "On other networks", i.e. the bucket is not a reliable proof of physical location — [Community, Spotify forum](https://community.spotify.com/forum/en/discussion/5680446/spotify-playback-queue-resets-when-trying-to-connect-between-devices); [Community, Spotify forum (Apple TV same Wi-Fi, shown as "other networks")](https://community.spotify.com/t5/iOS-iPhone-iPad/My-Apple-TV-isn-t-seen-from-the-same-Wi-Fi-in-Spotify-Connect/td-p/5933709).
- Spotify's consumer docs still claim "All devices must be connected to the same network" for Connect — [Official, Web Playback SDK concepts](https://developer.spotify.com/documentation/web-playback-sdk/concepts/spotify-connect) — which contradicts its own support article about remotely visible, credential-logged-in devices. Treat the "same network" statement as the pairing/first-run requirement, not a hard visibility rule.

### Inferences
- The device picker almost certainly renders two sets: devices for which the client has a live **local mDNS/ZeroConf** record ("this network" / "on this network"), and devices known only from the **account device list** returned by the Connect backend ("other networks"). The exact grouping/timing is undocumented. [Inference]
- A Chrome tab running `open.spotify.com` (or any Web Playback SDK app) lives only in the account plane: browsers cannot open a listening TCP port, cannot answer `getInfo`, and cannot publish DNS-SD records. It is therefore **structurally incapable** of appearing under "this network", even when it runs on the same laptop as the phone's Spotify client. This is the cleanest explanation for "Chrome appears under other networks". [Inference, from Official SDK + ZeroConf docs]
- An arbitrary network audio endpoint (Snapcast, AirPlay, raw HTTP stream, DLNA) has no Spotify account session and no `_spotify-connect._tcp` advertisement, so it has no entry in either plane. Spotify has no generic "cast to this URL" feature. [Inference]
- Two distinct things can be called "Chrome": (1) the **browser tab as a Connect playback device** (Web Playback SDK / web player), and (2) a **Chromecast/Cast-built-in target** discovered by the web player via Google Cast. Only (1) is a Spotify Connect device; (2) is a Cast device that Spotify can drive. The support text above treats them separately. [Inference]
- Because the account plane is authoritative, a device can be visible while being completely unreachable (stale cloud entry), and can be invisible while being reachable (mDNS blocked). This asymmetry explains most "ghost device" and "can't see my speaker" reports. [Inference]

### Gaps
- Spotify does not document the UI strings, thresholds, or ordering logic for "this network" vs "other networks", nor how long a device lingers in the account list after going offline.
- It is not documented whether the first-party web player uses the public Web Playback SDK internally or a private equivalent; only that it appears in `/me/player/devices`.
- No official statement on whether the mobile app performs active reachability probes on account-known devices before listing them, or lists them purely from cached cloud state.

## Q2. How does Spotify Connect discover devices: local zeroconf/mDNS, cloud account registration, or both? What determines "this network" vs "other networks"?

### Takeaway
**Both, for different jobs.** mDNS/ZeroConf is the LAN bootstrap and pairing channel (it yields IP, port, `CPath`, device identity, public key, and enables password-less login). The Spotify backend is the long-lived control plane: every logged-in client holds a session/device entry there, receives commands and state through it, and can be reached regardless of LAN topology. mDNS decides "local"; the account decides "known at all".

### Cited Findings
- ZeroConf is "an HTTP interface used for announcing and securely logging in to a hardware device… without the user entering a password". Requirements: an HTTP server, JSON, and "a mDNS discovery service compatible with Apple's Bonjour" — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf).
- DNS-SD service type is `_spotify-connect._tcp`; `SRV` carries IP/port; `TXT` carries `CPath` (field name is **case-sensitive**); example `CPath=/zeroconf` — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf); [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- `getInfo` returns: `version` (ZeroConf API version, e.g. `"2.10.0"`), `deviceID`, `publicKey`, `remoteName`, optional `deviceType`, `brandDisplayName`, optional `modelDisplayName`, `libraryVersion`, `resolverVersion`, `groupStatus`, `tokenType`, `clientID`, `productID`, `scope`, `availability`, optional `aliases`, optional `supported_drm_media_formats`, optional `supported_capabilities` — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf).
- `addUser` is a POST carrying `userName`, an encrypted `blob`, `clientKey`, and `tokenType`; the device must log in with `SpConnectionLoginZeroConf()`, must **not** persist the blob/clientKey, and must wait for login success before replying — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf); [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- ZeroConf also supports **device aliases**, letting one physical device announce several virtual devices (e.g. multiroom zones), each selectable in the app — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf).
- The cloud control channel is a **dealer websocket** that "represents the player as spotify-connect device"; it is "primarily used to receive updates and not to update the state". Incoming items are either informational messages, fire-and-forget commands (volume updates and logout are sent **only to the active player**), or **requests that modify player state** — [RE, librespot `docs/dealer.md`](https://github.com/librespot-org/librespot/blob/dev/docs/dealer.md).
- Before the dealer, clients resolve an access point via `http://apresolve.spotify.com`, open a bare TCP connection (no TLS/HTTP), do a Diffie–Hellman hello, then encrypt with the Shannon cipher — [RE, librespot `docs/connection.md`](https://github.com/librespot-org/librespot/blob/dev/docs/connection.md).
- go-librespot's Zeroconf mode "enables mDNS auto discovery, allowing Spotify clients inside the same network to connect"; `zeroconf_enabled: true` keeps it discoverable "at all times, even if authenticated via other means"; it can advertise only selected interfaces (`zeroconf_interfaces_to_advertise`) and can use either its built-in responder or Avahi — [RE, go-librespot README](https://github.com/devgianlu/go-librespot).
- go-librespot's **interactive OAuth** mode "allows you to associate your account with the device and make it discoverable **even outside the network**" — [RE, go-librespot README](https://github.com/devgianlu/go-librespot). This is direct evidence that cloud account registration, not mDNS, is what makes remote visibility possible.
- go-librespot also supports a **device-authorization** flow (code entered at `spotify.com/pair`) with no listening port at all — [RE, go-librespot README](https://github.com/devgianlu/go-librespot).
- Soloist "advertises itself on your local network, authenticates through Spotify Connect, and plays audio through the device's audio system"; the optional WebSocket API is explicitly "separate from Spotify Connect" — [Official, Soloist overview](https://developer.spotify.com/documentation/soloist/concepts/overview).
- In multiroom configurations, if ZeroConf is disabled on an inactive slave, "mDNS should be turned off. It's not enough to just turn off the webserver endpoints" — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf).

### Inferences
- The LAN plane is best understood as **pairing + locality metadata**, not as the playback transport. Playback commands and state flow over the cloud connection; mDNS only tells the controller "this device is here, here is its HTTP endpoint and its public key".
- "This network" therefore means "the controller currently has a valid local ZeroConf/mDNS record for this device". "Other networks" means "the account knows this device, but the controller has no local record" — which may be because it is genuinely remote, or because multicast is filtered, the device advertises on the wrong interface, or the device is a browser. [Inference]
- Because both planes exist, an implementation that only logs in (OAuth/device-auth) will work remotely but may never appear under "this network"; an implementation that only advertises mDNS will appear locally but cannot play without a Spotify session. Native devices do both. [Inference]
- Device identity (`deviceID`) is the join key between the two planes; it must be stable across reboots, otherwise credentials and cloud entries fragment (see Q5). [Inference]

### Gaps
- Spotify does not publish the cloud registry's API, its TTLs, or how a controller merges mDNS results with the cloud device list.
- No official documentation of the `deviceType` enumeration beyond examples (`SPEAKER`, `computer`, `smartphone`, `speaker`) or of which types get which icon.
- Whether the cloud list is per-account only, or also per "household"/family, is not documented; community reports of seeing other users' devices on shared networks suggest at minimum account-level persistence plus LAN leakage of unauthenticated device advertisements.

## Q3. What happens when the user selects a speaker on the phone, then later switches back to the phone? Which state is synchronised and how?

### Takeaway
Transfer is a **server-side change of the active device pointer**, not an audio handoff. Exactly one device is active and streams; all others receive the same logical state (context, track, position, queue, shuffle/repeat, per-device volume) and are expected to go silent. On switching back, the phone becomes active at the last known logical position; the speaker must stop immediately, flush buffered audio, and remain a visible, controllable, inactive device.

### Cited Findings
- "By selecting a wireless speaker in the Connect menu … playback will be transferred from the phone to the wireless speaker. The phone continues to work as a remote control, so the user can pause playback, skip tracks, or change the volume on the speaker by using the Spotify mobile app" — [Official, Spotify Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics).
- The device receives `kSpPlaybackNotifyBecameActive` on transfer; when the phone pauses, it receives `kSpPlaybackNotifyPause`; on transfer away it receives `kSpPlaybackNotifyBecameInactive` and must stop — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics).
- "Only the active device plays audio. You must receive `kSpPlaybackNotifyBecameActive` in order to be allowed to play audio" — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics).
- State getters "reflect the state of the playback **among all Connect-enabled devices, even if the device is not the active playback device**" — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics).
- Synchronised metadata enumerated by the SDK: current/previous/next track (track, artist, duration), playback position, playing/paused, shuffle on/off, repeat on/off (3-state: off / repeat context / repeat track), plus per-track playback restrictions — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics).
- Volume is **per device**, not carried by transfer: the app invokes `SpCallbackPlaybackApplyVolume` on the device; if the device's own knob changes volume it must call `SpPlaybackUpdateVolume()` so remotes update. On init the SDK assumes maximum volume (65535) until told otherwise — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics).
- Buffering is device-local and deliberately large: eSDK buffers 256 KB by default (~21 s at 96 kbit/s, ~13 s at 160, ~6 s at 320) and up to 5 MB (~436/262/131 s), specifically so playback continues through network outages — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs). This is also why the UI position and the audible position can diverge.
- Switching a speaker away from Spotify input while active: call `SpPlaybackPause()`; "this will cause the mobile app to display the audio as paused, but the speaker will remain the active device" — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- If the user moves playback to the speaker while it is on AUX/Internet Radio, the device gets `kSpPlaybackPlay` and `kSpPlaybackNotifyBecameActive`, and should switch input to Spotify — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- If the device can no longer be controlled, it must log out and **stop announcing** `spotify-connect._tcp`; otherwise "the speaker would still appear in the Connect device picker … even though the speaker would no longer react to commands" — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- Transfer via Web API is `PUT /me/player` with `device_ids` (array accepted but "only a single device_id is currently supported"; more than one → 400) and optional `play` (true forces playback; false/omitted keeps current state); Premium only; scope `user-modify-playback-state` — [Official, Transfer Playback](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback). "The order of execution is not guaranteed when you use this API with other Player API endpoints" — same source.
- Device object exposes `is_active`, `is_private_session`, `is_restricted`, `name`, `type`, `volume_percent`, `supports_volume`; `is_restricted: true` means **no Web API commands will be accepted** by that device — [Official, Get Available Devices](https://developer.spotify.com/documentation/web-api/reference/get-a-users-available-devices).
- Spotify Support warns: "If you pause playing for more than 10 minutes, you might need to reconnect" — [Official, Spotify Connect support](https://support.spotify.com/us/article/spotify-connect/).
- Implementations report the same model: go-librespot advertises "Podcast resume — episodes pick up where you left off, and **progress syncs back to your other devices**" — [RE, go-librespot README](https://github.com/devgianlu/go-librespot).
- Music Assistant documents the transfer semantics from the controller side: "Stopping playback in Music Assistant **releases the device** in the Spotify app; moving playback to another device in the Spotify app **stops the MA player**" — [Music Assistant docs, Spotify Connect plugin](https://www.music-assistant.io/plugins/spotify-connect/).
- MA also warns about skew: "Depending on the player's own buffering there can be a short delay between an action in the Spotify app and hearing the result, and the **Spotify app's progress can run slightly ahead of the audio**" — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).
- Queue semantics are asymmetric: the Web API can add to the queue, but as of the 2022 Player API write-up there was "no API yet for removing tracks from the queue, or for reading the contents of the queue" — [Official, Spotify Engineering](https://engineering.atspotify.com/2022/04/spotifys-player-api). Reverse-engineered clients must handle queue UIDs carefully; librespot synthesises `uid`s for contexts that lack them because otherwise official clients "get confused and send incorrect data via the `set_queue` request" — [RE, librespot `docs/dealer.md`](https://github.com/librespot-org/librespot/blob/dev/docs/dealer.md).

### Inferences
- The authoritative session state lives in Spotify's backend (the "cluster"/player state mutated by dealer requests). Every client is a view plus, for the active one, an audio renderer. Transfer changes which device is allowed to render; it does not move buffers, sockets, or decoded audio. [Inference, from dealer doc + active-device rules]
- What transfers: context/queue, current track, logical position, play/pause, shuffle/repeat, restrictions, and (for some clients) DJ/autoplay metadata. What does **not** transfer: volume (device-local), audio buffer, output latency, EQ/normalisation settings, and local-only features. [Inference]
- Position reconciliation is inherently approximate. The outgoing device may have several seconds buffered; the incoming device starts from the backend position. A correct implementation must stop and flush on `BecameInactive` rather than drain its buffer, or both devices will be audible. [Inference]
- Quick A→B→A switching is the harshest test: it exercises stale active-device flags, double-audio, and queue rewrites. The documented "not guaranteed ordering" of Player API calls plus the 10-minute reconnect warning suggest the backend tolerates but does not serialise aggressive control changes. [Inference]
- Because the phone remains a controller, "switching back to the phone" is just another transfer; the phone's own player resumes streaming, and the speaker stays in the picker as inactive rather than disappearing (unless it logs out / stops announcing). [Inference]

### Gaps
- No public spec for the exact state message schema, position timestamping/clock sync, or how the backend arbitrates two controllers issuing conflicting commands in the same second.
- Spotify does not document whether queue contents are guaranteed identical across clients, nor how "next" is resolved when clients disagree about context iteration (librespot's repeat implementation is admittedly a mimic, not a spec).
- No official data on how long an inactive device remains addressable, or on server-side timeouts for a device that stops sending heartbeats.

## Q4. What is the role of the official Connect SDK / partner program versus reverse-engineered implementations (librespot, go-librespot) and Soloist — and what must a third-party device do to look native?

### Takeaway
There are now **three viable paths**, with very different legitimacy and effort: (1) the **commercial eSDK**, available only to approved partners and requiring certification; (2) **Spotify Soloist**, an official headless binary (2026) that any DIY user can run with a per-user API key; (3) **librespot / go-librespot**, reverse-engineered clients that work today but are explicitly unsupported and can break at any time. All three implement the same visible contract: mDNS advertisement + `getInfo`/`addUser` + a Spotify Connect session + local audio rendering + full state/volume/lifecycle handling.

### Cited Findings
- Commercial Hardware tools and the eSDK "are available only for approved partners"; partners must go through onboarding and certification, and "hardware partners must only use the embedded SDK" (not the Web API) — [Official, Commercial Hardware](https://developer.spotify.com/documentation/commercial-hardware); [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- eSDK provides the full state machine (playback notifications, metadata, restrictions, volume, active/inactive, audio callbacks) and the option of a built-in ZeroConf server; if it is not used, the partner "must implement" the ZeroConf API — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf).
- Spotify Free on hardware is possible only on eSDK build 3+ ("Spotify Free is only available for eSDK builds 3 and above") — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs). This contradicts the common assumption that Connect is Premium-only; it is product- and build-dependent.
- **Soloist** (announced 2026-08-13): "a new Spotify Connect terminal client for headless and DIY setups… runs on Raspberry Pis and Linux, works with both Free and Premium Spotify accounts"; "A Premium account is needed to set up Spotify Soloist, but once it's running both Free and Premium users can connect"; "built on the same powerful playback engine as the Spotify desktop and mobile apps"; includes Jam, lossless up to 24-bit/44.1 kHz, crossfade/automix, and a local WebSocket API with queue metadata for up to 80 upcoming tracks — [Official, Spotify for Developers blog](https://developer.spotify.com/blog/2026-08-13-introducing-spotify-soloist).
- Soloist builds are **time-limited to 90 days** from build date; it logs remaining lifetime and exits with code `10` when expired — [Official, Soloist overview](https://developer.spotify.com/documentation/soloist/concepts/overview).
- Soloist requires a per-user **API key** generated at `/dashboard/soloist` by a **Premium** account; the key must not be shared, published, embedded client-side, or put in distributed scripts; it is required at every startup even when restoring a session — [Official, Soloist authentication](https://developer.spotify.com/documentation/soloist/concepts/authentication).
- Soloist pairing is itself a Connect flow: start it, open the Spotify app on the same LAN, select the device; it authenticates and stores the session; keep the data directory to stay paired; `--pair` re-pairs — [Official, Soloist authentication](https://developer.spotify.com/documentation/soloist/concepts/authentication).
- Soloist's WebSocket API "has no built-in client authentication, authorization, TLS, Origin validation, CSRF protection…"; bind to `127.0.0.1` for local integrations — [Official, Soloist overview](https://developer.spotify.com/documentation/soloist/concepts/overview).
- Soloist has no local UI: "you can start playback, transfer playback, control the queue, adjust volume, shuffle, and repeat from Spotify apps, while audio plays on your device" — [Official, Soloist features](https://developer.spotify.com/documentation/soloist/features).
- **librespot** is "an open source client library for Spotify… act as a Spotify Connect receiver"; "librespot only works with Spotify Premium. This will remain the case"; its own README says "Using this code to connect to Spotify's API is probably forbidden by them. Use at your own risk" — [RE, librespot README](https://github.com/librespot-org/librespot).
- librespot implements the real client protocol: AP resolution, DH handshake + Shannon encryption, blob/ZeroConf/password auth, dealer websocket, Mercury, spclient, audio keys and CDN playback — [RE, librespot docs](https://github.com/librespot-org/librespot/tree/dev/docs).
- **go-librespot** is a Go reimplementation: "show up as a speaker in the Spotify app and stream to it from any device on your network (Spotify Premium required)"; it supports builtin/Avahi mDNS, Zeroconf/interactive/device-auth login, a REST + WebSocket API, MPRIS, and configurable volume/mixer behaviour — [RE, go-librespot README](https://github.com/devgianlu/go-librespot).
- Music Assistant positions the two engines bluntly: **Soloist** = "official, recommended", requires a Premium account once to create the API key, then Free or Premium clients can connect, lossless up to 24/44.1 for supported Premium accounts; **go-librespot** = "community… reverse-engineered… intended for Spotify Premium accounts created before December 2024 and may stop working whenever Spotify changes things on their end" — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/). The "created before December 2024" constraint is MA's claim; I found no Spotify or go-librespot statement confirming the cutoff.
- MA also notes it "may not distribute Soloist as part of its own installation", downloading it from Spotify's servers after consent, and that "Spotify's terms do not clearly allow using Soloist this way — using it through Music Assistant is at your own risk" — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).
- Lossless is not available to librespot-class devices as of late 2026: a September 2026 Spotify Community thread is a feature request to "Enable Spotify Lossless (FLAC) via Spotify Connect for third-party librespot-based devices" — [Community, Spotify forum, 2026-09-13](https://community.spotify.com/forum/en/discussion/7554102/enable-spotify-lossless-flac-via-spotify-connect-for-third-party-librespot-based-devices). [Community signal, not an official statement]
- The Web Playback SDK is not a substitute for a speaker: it is browser-only, requires Premium (mobile-only Premium excluded), needs an access token refreshed hourly, may be blocked by autoplay policy on transfer unless `activateElement()` was called, and "must not be used in commercial projects without Spotify's prior written approval" — [Official, Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk); [Official, getting started](https://developer.spotify.com/documentation/web-playback-sdk/tutorials/getting-started).
- The Web API player endpoints are a **controller**, not a receiver: they can transfer/command playback but cannot make an endpoint render audio — [Official, Transfer Playback](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback).

**Implementation contract (what "looks native" requires), synthesised from the above:**
1. **Stable identity**: persistent `deviceID` + persisted credentials in a stable data dir; changing it invalidates stored blobs ("Parsing ZeroConf blob failed with code -3" if `unique_id` changes) — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
2. **DNS-SD**: `_spotify-connect._tcp`, `SRV` host/port, `TXT CPath=/...` (case-sensitive), advertised on the reachable interface only; withdraw the record when the device is no longer controllable — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf); [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
3. **HTTP ZeroConf**: `GET ?action=getInfo` returning valid UTF-8 JSON with all required fields and correct `version`; `POST ?action=addUser` performing the real login and replying only after success; optional `resetUsers`; HTTPS preferred — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf).
4. **Connect session**: authenticated dealer/spclient connection, handling requests (play/pause/seek/next/prev/volume/shuffle/repeat/set_queue) and informational updates — [RE, librespot `docs/dealer.md`](https://github.com/librespot-org/librespot/blob/dev/docs/dealer.md).
5. **Audio pipeline**: access point → encrypted audio (Ogg Vorbis/FLAC/MP3), per-track audio key, decrypt, decode, buffer, clocked output, loudness normalisation (−14 LUFS) and optional crossfade — [RE, librespot docs](https://github.com/librespot-org/librespot/tree/dev/docs); [RE, go-librespot README](https://github.com/devgianlu/go-librespot).
6. **State surface**: current/next/previous metadata, position, playing, shuffle, repeat (3-state), restrictions, volume percent + `supports_volume`, `is_restricted`, private session — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics); [Official, Get Available Devices](https://developer.spotify.com/documentation/web-api/reference/get-a-users-available-devices).
7. **Lifecycle**: pause + `BecameInactive` handling on transfer away, audio flush, resume on `BecameActive`, pause (not logout) on input switch/standby, no autoplay on boot, logout + stop mDNS when unreachable — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics); [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
8. **Presentation**: `remoteName`/brand/model, `deviceType` for the icon, `groupStatus`/`aliases` for multiroom — [Official, ZeroConf API](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/zeroconf).

### Inferences
- For a DIY speaker in 2026, **Soloist is the lowest-risk native-looking path**: it is first-party, supports Free listeners, exposes a local WebSocket control surface, and avoids protocol reverse-engineering. The costs are the 90-day build treadmill, the per-user Premium-gated API key, and the fact that redistribution/integration terms are unclear. [Inference]
- librespot/go-librespot remain the fallback when Soloist is unavailable (platform, licensing, or account constraints), but they are a moving target: Premium-only, no lossless, and explicitly "probably forbidden". [Inference]
- The commercial eSDK is effectively out of reach for a hobby project: partner approval, certification, C integration, and a contractual relationship. [Inference]
- "Native behaviour" is mostly about the **unglamorous edges** — stable IDs, correct JSON escaping, stopping on transfer, not auto-playing on boot, withdrawing mDNS — not about the audio codec. Most third-party devices that "work but feel wrong" fail on lifecycle, not decoding. [Inference]

### Gaps
- No public Soloist source/licence statement covering redistribution in a product; the GitHub repo exists but terms for embedding are not clear from the docs reviewed.
- No official statement on whether Soloist will remain free, whether the 90-day expiry is permanent, or whether API keys will be rate-limited/revoked for DIY use.
- No authoritative explanation of go-librespot's "Premium accounts created before December 2024" limitation; I could not verify whether it is an authentication-protocol change, a licensing enforcement, or an MA-specific observation.
- Exact lossless support matrix for third-party devices in 2026 is undocumented; only MA's claim (Soloist up to 24/44.1) and a community feature request for librespot.

## Q5. What are the account/stream limits (one active stream, Premium requirements, device limits) and the likely failure modes?

### Takeaway
The binding constraint is **one active playback stream per account**, enforced by the active-device model, not a documented "N devices" cap on the Connect list. Premium is required for the Web API player, the Web Playback SDK, and librespot; Free can work on eSDK build 3+ and on Soloist after a Premium key is created. The 5-device limit is for **offline downloads**, not streaming. Most real-world failures are discovery/lifecycle failures, not account limits.

### Cited Findings
- Only the active device plays audio and must receive `BecameActive` before playing — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics). Transferring to a speaker therefore necessarily stops the phone's stream.
- Web API player endpoints (transfer/play/pause/seek/volume/queue) "only works for users who have Spotify Premium" — [Official, Transfer Playback](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback); [Official, Start/Resume Playback](https://developer.spotify.com/documentation/web-api/reference/start-a-users-playback).
- Web Playback SDK requires Premium; "mobile only types of premium subscriptions are excluded" — [Official, Web Playback SDK](https://developer.spotify.com/documentation/web-playback-sdk).
- librespot: "only works with Spotify Premium. This will remain the case. We will not support any features to make librespot compatible with free accounts, such as limited skips and adverts" — [RE, librespot README](https://github.com/librespot-org/librespot).
- eSDK can support Free on build 3+ — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs). Soloist needs Premium only to create the API key; afterwards Free clients can connect — [Official, Soloist blog](https://developer.spotify.com/blog/2026-08-13-introducing-spotify-soloist); [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).
- Offline limits are separate: "10,000 tracks on each of up to 5 different devices", online at least once every 30 days — [Official, Listen offline](https://support.spotify.com/us/article/listen-offline/). Do not confuse this with Connect device count.
- Some devices are simply not exposed to the API: "Some device models are not supported and will not be listed in the API response" — [Official, Get Available Devices](https://developer.spotify.com/documentation/web-api/reference/get-a-users-available-devices).
- `device_id` is nullable and only "unique and persistent to some extent… not guaranteed and any cached device_id should periodically be cleared out and refetched" — [Official, Get Available Devices](https://developer.spotify.com/documentation/web-api/reference/get-a-users-available-devices).
- `is_restricted: true` means "no Web API commands will be accepted by this device" — [Official, Get Available Devices](https://developer.spotify.com/documentation/web-api/reference/get-a-users-available-devices).
- API responses include `401`, `403`, `429` — [Official, Transfer Playback](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback); `429` implies rate limiting that a polling controller can hit.
- Discovery failure checklist (official): missing/incorrect `SRV`/`TXT CPath`, case-sensitive field name, HTTP server not bound to the announced interface, firewall, invalid JSON, wrong `version`, missing required fields, unescaped special characters — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- mDNS across VLANs requires a reflector; without it, discovery fails even with routed IP — [Community, OpenWrt](https://forum.openwrt.org/t/spotify-connect-with-different-vlans-does-not-work-even-with-mdns/169860).
- A device that does not stop announcing when it becomes uncontrollable stays in the picker as a ghost — [Official, FAQ](https://developer.spotify.com/documentation/commercial-hardware/implementation/faqs).
- Pausing >10 minutes may require reconnecting — [Official, Spotify Connect support](https://support.spotify.com/us/article/spotify-connect/).
- On shared networks, users see other people's devices; Spotify's remedy is "Local device visibility", removing the device, or "Log out of this device" — [Official, Spotify Connect support](https://support.spotify.com/us/article/spotify-connect/).
- Community reports of playback/queue resets when switching between devices that are mislabelled "On other networks" — [Community, Spotify forum](https://community.spotify.com/forum/en/discussion/5680446/spotify-playback-queue-resets-when-trying-to-connect-between-devices).

### Inferences
- There is no publicly documented hard cap on how many Connect devices can be *listed* for one account; the practical cap is one **active stream**. Multiple devices can be online, visible, and controllable; exactly one renders audio. [Inference]
- Effective failure taxonomy:
  1. **Not discovered** — mDNS filtered (VLAN/AP isolation/guest Wi-Fi), wrong interface, Docker/Avahi conflict, firewall, `CPath` typo, HTTP bind on wrong address.
  2. **Discovered but unresponsive** — stale cloud entry, crashed process that still advertises, device slept without withdrawing records.
  3. **Visible in cloud, not local** — appears under "other networks"; often works but with higher latency and occasional "device not found".
  4. **Auth/session** — expired token/blob, changed `unique_id`, account logged out elsewhere, Premium lapsed, Free account on a Premium-only client.
  5. **Control-plane** — 404 device not found (stale `device_id`), 403 restricted/private session, 429 rate limit, command reordering.
  6. **State/audio** — double audio on slow transfer, position drift, queue divergence, volume fight with a local mixer.
  7. **Account hygiene** — another person's session on the same account, devices from a shared network, "ghost" entries that must be logged out. [Inference]
- Because `device_id` persistence is explicitly not guaranteed, any integration that stores a device ID (Home Assistant, MA, a local controller) must re-resolve it via `/me/player/devices` on failure rather than treating it as a primary key. [Inference]
- A Free account is not a reliable target for a DIY receiver unless the chosen engine is Soloist or an eSDK build ≥3; the Web API path will simply fail. [Inference]

### Gaps
- Spotify does not publish a formal "one stream per account" policy page that I could find; the rule is inferred from the active-device model and enforced in practice. No documented number of simultaneous *sessions*/devices.
- No official figures for device-list TTL, heartbeat interval, or how long a stale device remains selectable.
- No documented behaviour for two devices claiming the same `deviceID`, or for the same account playing via two independent reverse-engineered clients simultaneously (whether the backend allows a brief overlap).
- Rate-limit specifics (quota window, per-app vs per-user) are not in the reference pages reviewed.

## Q6. Can a third-party open-source device appear in the official app while also being controlled locally by another system (Home Assistant / Music Assistant)? What conflicts arise?

### Takeaway
**Yes — and this is the normal architecture, not a hack.** A Connect receiver is a device with one Spotify session and potentially many controllers. The official app, Music Assistant, Home Assistant, MPRIS, and a vendor remote all send commands into the same session; there is no ownership or locking. Coexistence works when one system is the source of truth for "what should play" and the other is a thin remote; it breaks when both run autonomous control loops.

### Cited Findings
- Music Assistant's Spotify Connect plugin exposes "any MA player (or group of players)" in the Spotify device list "just like an official Spotify Connect speaker"; each selected player is advertised as its own Connect device, with configurable name pattern (`Player name | Music Assistant`, etc.) — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).
- MA supports two engines (Soloist official / go-librespot community) and documents the interplay explicitly: playback can be started from MA itself, which "resumes your last Spotify session on the device"; "Stopping playback in Music Assistant **releases the device** in the Spotify app"; "moving playback to another device in the Spotify app **stops the MA player**" — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).
- MA warns that Home Assistant players are "supported but not recommended — your mileage may vary", and that "Native Music Assistant players work best" — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).
- go-librespot exposes a local REST API + WebSocket events (`server.address: localhost`, port 3678 by default) for control and monitoring, alongside the Spotify Connect session — [RE, go-librespot README](https://github.com/devgianlu/go-librespot).
- Soloist's optional WebSocket API lets "another local process observe playback events and send playback commands"; it has **no authentication, authorization, TLS, Origin validation, or CSRF protection**, and should be bound to loopback — [Official, Soloist overview](https://developer.spotify.com/documentation/soloist/concepts/overview); [Official, Soloist features](https://developer.spotify.com/documentation/soloist/features).
- The eSDK explicitly supports local control surfaces: hardware buttons/knobs call `SpPlaybackUpdateVolume()` etc., and those local changes must be propagated so "Connect-enabled remote control apps can update the volume of the speaker in their UIs" — [Official, Connect Basics](https://developer.spotify.com/documentation/commercial-hardware/implementation/guides/connect-basics). The same section documents four volume-sync modes in go-librespot: Spotify-only, Spotify↔ALSA mixer both ways, external volume, external volume with mixer — [RE, go-librespot README](https://github.com/devgianlu/go-librespot).
- Soloist offers a similar choice: "Player volume only" (audio untouched) or syncing the app's volume slider with the player volume — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).
- The official app can remove/expire devices: "Log out of this device" from the three-dot menu, or "Sign out everywhere" — [Official, Spotify Connect support](https://support.spotify.com/us/article/spotify-connect/).
- MA documents latency/clock caveats that become conflicts when two systems display state: buffering delay, and "the Spotify app's progress can run slightly ahead of the audio" — [Music Assistant docs](https://www.music-assistant.io/plugins/spotify-connect/).

### Inferences
- **Supported pattern**: Spotify app = human-facing remote; MA/HA = automation layer that issues discrete commands (play this playlist, set volume, pause) and reads state. One session, many controllers; last command wins. This is how MA's plugin is designed. [Inference]
- **Conflict pattern A — volume fight**: if the speaker syncs Spotify volume to a local mixer *and* HA also writes the mixer, each write is echoed back as a Spotify volume change, producing oscillation. Fix: single owner of the volume mapping; use "external volume" mode or disable one direction. [Inference]
- **Conflict pattern B — transport fight**: an automation that resumes playback on motion will immediately undo a user's pause from the phone, and vice versa. There is no arbitration API, so this must be solved in the automation (conditions, grace periods, "manual override" flags). [Inference]
- **Conflict pattern C — queue/context rewrite**: a local controller that calls `play` with a context replaces the queue; the phone then shows a different "Up next" than the user built. Queue is server-side, so there is only one queue — whoever writes last defines it. [Inference]
- **Conflict pattern D — device identity**: two processes must not share a `deviceID`; and deleting the data dir / re-pairing creates a new identity, leaving a ghost entry in the app and breaking cached IDs in HA. [Inference]
- **Conflict pattern E — release semantics**: if the local system "stops" by killing the audio pipeline without pausing/logging out, the device stays active-but-silent in the app; the user sees "playing" with no sound. MA's documented behaviour (stop releases the device; transfer away stops the player) is the correct model to copy. [Inference]
- **Security**: exposing Soloist's or go-librespot's local API beyond loopback gives anyone on the LAN unauthenticated playback control of the account's active session. On a shared/guest network this is equivalent to handing over the remote. [Inference, from Official Soloist warning]
- A local controller does **not** create a second stream: it controls the same device/session, so it does not violate the one-active-stream model. A second *receiver* logged into the same account would compete for the active slot instead. [Inference]

### Gaps
- No official documentation of multi-controller semantics (locking, command priority, conflict resolution); behaviour must be discovered empirically per client.
- MA's plugin internals (how it reconciles its own queue with Connect state, how it detects external transfers) are not documented beyond the user-facing statements; the source would be needed for exact behaviour.
- No data on whether Spotify penalises accounts that frequently transfer between many devices or run multiple reverse-engineered clients; only anecdotal reports of sessions being logged out.
- Whether Soloist's WebSocket API will gain authentication before it is recommended for production integrations is unknown.

### Cross-cutting source-quality note for the report writer
- The **official** Connect documentation is split across three places that do not fully agree: Commercial Hardware/eSDK (device-side, partner-only), Web Playback SDK/Web API (controller/browser-side), and Support articles (consumer-facing). The consumer claim "all devices must be on the same network" is contradicted by the support article's own remote-visibility instructions; prefer the latter for behaviour, the former for first-run pairing.
- The **protocol details** (dealer, AP handshake, blob auth) come from librespot's docs, which are reverse-engineered and may lag Spotify changes; they are the best public description but not normative.
- The **"other networks" bucketing** is consistently described by users and consistent with the two-plane model, but Spotify never documents the UI logic. Present it as a strongly supported inference, not a fact.
- Soloist (Aug 2026) materially changes the "third-party device" answer versus the pre-2026 librespot-only landscape; any report should be explicit about the date.
