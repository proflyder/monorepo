# Spike: «Рикардо ↔ bb» — Hermes как провайдер bb или Hermes как клиент bb

Дата: 2026-11-20. Задача владельца: голосом/из Telegram ставить задачи, которые
живут как bb-треды, и получать итог обратно.

Документ фиксирует замеры и решение. Ничего в проде не менялось: тестовые треды
удалены, образ Hermes не пересобирался, манифесты не правились.

## Итог

**Вариант 2 (Hermes вызывает bb через mcp-gateway) — делать.**
**Вариант 1 (bb запускает Hermes как ACP-провайдера) — не делать для голоса.**

Причины коротко:

- Путь «Hermes → mcp-gateway → SSH → bb-dispatch → плагин → bb SDK» уже
  существует и работает: `bb_status` отвечает **0.14–0.23 с**, `spawn` —
  **3.1 с**, `send` — **0.35 с**, чтение итога — **0.06 с**. Это укладывается в
  голосовой бюджет, если убрать одну поломку (`targets` = 12 с).
- Hermes как ACP-провайдер bb технически возможен (в закреплённой ревизии есть
  `hermes acp`), но каждый тред — отдельный процесс Hermes: 1.1 с на старт
  (тёплый) и +0.45 с на сессию, память и конфиг расходятся с пода, а голосовой
  ход получает лишние ~0.4 с диспетчеризации bb и второй LLM-цикл.
- Вариант 2 сохраняет сегодняшнюю латентность быстрых ответов (её не трогаем) и
  добавляет новую функцию отдельными инструментами.

## Вариант 1: Hermes как ACP-провайдер bb

### Что подтверждено

- В закреплённой ревизии `bf0203a7` есть полноценный ACP-сервер:
  `hermes acp`, пакет `acp_adapter/` (6518 строк), точка входа
  `hermes-acp = "acp_adapter.entry:main"`, extra `acp =
  agent-client-protocol==0.9.0`.
- Адаптер умеет то, что нужно bb: `session/new|load|resume`, стриминг
  `agent_message_chunk`, tool-call апдейты, `session/set_model`, режимы
  `default|accept_edits|dont_ask`, отдельные MCP-серверы из клиента **и** свои
  `mcp_servers` из `config.yaml`.
- bb находит его сам: в каталоге есть готовый провайдер `acp-hermes-agent`
  (команда `hermes`), как только `hermes` появляется в `PATH` машины.
- Проверено на Mac с установкой ровно этой ревизии: `hermes acp --check` → OK,
  ACP `initialize` отвечает, `session/new` отдаёт 19 моделей и сессию.

### Что мешает

1. **В образе нет extra `acp`.** В поде
   `hermes acp --check` → «protocol packages are missing», `No module named
   'acp'`. Нужно добавить `acp` в `uv sync --extras` в
   `projects/home-assistant/deploy/images/hermes/Dockerfile`, пересобрать и
   перепинить образ (изменение образа, не конфига).
2. **bb запускает `hermes acp` вне пода.** Второй экземпляр Hermes со своим
   `HERMES_HOME`: без `env`-настройки провайдер падает
   (`storage_unavailable`), а дефолтная модель выбирается неверно
   (`openai-codex:anthropic/claude-opus-4.6`) — модель надо задавать явно.
3. **Старт процесса.** Холодный первый запуск — 6.5 с, тёплый — 1.1 с + 0.45 с
   на сессию. Для треда, который живёт минутами, это амортизируется; для
   «тред на разговор» — нет.
4. **Ресурсы.** bb живёт в CT с 2 ГБ RAM (свободно ~1.4 ГБ). Hermes-процесс на
   каждый активный тред — это единицы сотен мегабайт. Несколько голосовых
   тредов + MCP-клиенты в этот CT не влезают.
5. **Конфиг и секреты.** Конфиг Hermes (`config.yaml`, `SOUL.md`, промпты,
   скиллы) сейчас доставляется в под init-контейнером из образа
   `hermes-config`; токены — из `Secret/hermes-environment` (ESO из OpenBao).
   Вне пода это второй рендер и вторая доставка секретов (fnox/OpenBao на
   хосте), то есть две точки правды для «Рикардо».
6. **Память разговоров.** ACP-сессии Hermes хранятся в его state DB
   (`source="acp"`) отдельно от сессии `api_server`, которую использует голос
   сегодня. Один и тот же «Рикардо» получит две несвязанные истории.

Вывод: как способ дать bb «ещё одного агента» — годится; как способ провести
через bb голосовой путь — нет.

## Вариант 2: Hermes вызывает bb (то, что нужно владельцу)

### Что уже есть в репозитории и в живом контуре

- `solutions/bb-home-dispatcher` — плагин bb с семью закрытыми методами
  (`targets`, `status`, `validate_spawn`, `spawn`, `send`, `turn_result`,
  `updates`), двухслойной аутентификацией (plugin token + HMAC-SHA256,
  окно ±30 с, тело ≤16 КиБ) и жёсткими границами: нет терминалов, файлов,
  удаления, произвольных команд.
- `projects/home/proxmox/bb/bb-dispatch` — SSH forced command на CT `bb`:
  один JSON из stdin, подпись, POST на loopback-маршрут плагина.
- `solutions/mcp-gateway` (`bb.read`/`bb.act`): `bb_status`,
  `bb_prepare_spawn` → `bb_confirm` / `bb_cancel`, плюс `/v1/voice/updates`
  long-poll для голосового объявления результатов.
- Плагин `home-dispatcher` живёт на CT `bb` (`path:/home/bb/bb-plugins/...`),
  `workerLimit=2`, `permissionMode=auto`, `dispatcherThreadId` настроен.

То есть «Hermes → bb» — это не новая интеграция, а расширение существующей.

### Что сломано прямо сейчас

`bb_prepare_spawn` в живом контуре отвечает «Сервер агентов недоступен»
(`bridge_error`) за 11.7–15 с. Причина найдена замерами:

- `targets` собирает **все** проекты профилей и для каждого опрашивает
  каталог моделей всех разрешённых провайдеров: **11.7–12.1 с**, ответ
  **100 864 байта** (8 проектов × до 5 провайдеров × модели с reasoning-уровнями).
- `validate_spawn` после этого — ещё 2.2–2.5 с, `spawn` — 3.1 с. Бюджет
  одного SSH-вызова 15 с, поэтому цепочка `prepare` либо упирается в таймаут,
  либо отдаёт неразобранный ответ.

`status`, `send`, `turn_result`, `updates` при этом быстрые (0.03–0.35 с) —
значит мост, ключи и маршрут в порядке, дело только в `targets`.

### Как выбирать проект, провайдера, модель и хост

- **Проект.** Сегодня `bb-targets.yaml` перечисляет личные проекты с
  голосовыми алиасами (`стан лэб`, `инглиш нотс`). Тот же файл — место для
  рабочего проекта: профиль `work` в bb это не отдельный сервер, а изоляция
  `CLAUDE_CONFIG_DIR`/`CODEX_HOME` внутри одного bb (`bb profiles list`:
  `jira-claude-workspace` → `work`, остальные → `personal`). Значит «по работе»
  реализуется добавлением цели в allowlist, а не вторым сервером.
- **Провайдер.** Живой каталог на машине проекта: `codex` (10 моделей),
  `claude-code` (13), `acp-opencode` (99), `pi`, `acp-cursor`,
  `acp-hermes-agent`. Фразы → id: «через клода» → `claude-code`,
  «кодекс/gpt» → `codex`, «дешёвым/дипсиком/через опенкод» → `acp-opencode`,
  «через пи» → `pi`. Дефолт — пин в `bb-targets.yaml`, иначе первый
  разрешённый политикой профиля.
- **Effort.** Дефолт `low` (требование владельца); «подумай как следует» →
  `high`. Значение всё равно валидируется по `reasoningLevels` модели.
- **Хост.** Все проекты сейчас имеют источник на Mac
  (`host_3upmsgn7d4`), у CT `bb` источников проектов нет, `DESKTOP-BABJJRM`
  отключён. Следствие: **пока Mac спит, ни одна задача не запустится**
  (`machine_offline` в `validate_spawn`, статус машины в `targets.machine`).
  bb различает это явно: `status: disconnected`, `online: false`,
  `lastSeenAt`; треды на уснувшей машине просто встают, id сохраняется.
  Для «работает всегда» нужен хотя бы один источник проекта (checkout) на
  CT `bb` или на k3s-хосте, зарегистрированном как машина bb.

## Предлагаемые MCP-инструменты

Группа `bb.read` — только чтение, кэшируется, без подтверждений;
группа `bb.act` — мутации, где дорого/необратимо — двухшаговое подтверждение.

| Инструмент | Параметры | Кратко голосу | Полно в Telegram / details |
|---|---|---|---|
| `bb_projects` | — | «Станция лаб, инглиш, джира» | id, профиль, машина, онлайн, дефолтный провайдер/модель, число активных тредов |
| `bb_machines` | — | «Мак в сети, неттоп в сети, ПК спит» | hostId, online, lastSeen, роль (=server), лимит разрешений |
| `bb_providers` | `project?` | «Клод, Кодекс, дешёвый» | model id/name, reasoning-уровни, дефолт, ошибки загрузки каталога |
| `bb_threads` | `query?`, `project?`, `status?`, `limit=5` | «Нашёл тред „Будильники“, вчера» | id, title, проект, статус, последний ход, выдержка |
| `bb_thread_read` | `threadId` | «Идёт, последний ответ: …» | статус, последний ответ (≤600 симв.), ждёт ли подтверждения, ref |
| `bb_task_prepare` | `project?`, `task`, `provider?`, `model?`, `effort?`, `machine?` | вопрос на подтверждение | resolved project/provider/model/effort, машина, TTL 90 с |
| `bb_task_start` | — (из pending) | «Запустил „…“ в станция лаб, пришлю в Телеграм» | threadId, ref, провайдер/модель, окружение |
| `bb_task_tell` | `threadId`, `text` | «Передал» | delivery (sent/queued), afterSeq, курсор |
| `bb_task_status` | `threadId?` | «Идёт 4 минуты: …» | running/recent, runtimeSeconds, статус, ждёт ли ввода |
| `bb_task_result` | `threadId`, `afterSeq?` | «Готово: …» (строка `🔊`) | полный текст, spoken, completedSeq, ошибка |
| `bb_task_cancel` | `threadId` + подтверждение | «Останавливаю?» | статус после stop |

Правила разрешения неоднозначностей (одна уточняющая реплика, всегда):

1. Проект: точный алиас → иначе единственное вхождение подстроки → иначе
   вопрос с ≤3 вариантами; «по работе» — отдельный алиас рабочего проекта.
2. Тред: ищем по `bb thread search` в пределах проекта из фразы; если
   кандидатов больше одного — «тот, что про будильники, или вчерашний?».
3. Провайдер/модель: фраза → id; если провайдер не разрешён политикой
   профиля или недоступен на машине — не угадываем, называем доступные.
4. Хост: по умолчанию машина источника проекта; при `online: false` —
   предложение запустить на доступной машине либо отказ «Мак спит».

Затратные/необратимые действия — только через подтверждение: `spawn`
(тратит токены, пишет в репозиторий), `cancel`, отправка в чужой проект.
Остальное (`status`, `thread_read`, `result`) — без подтверждений.

### Минимальный первый этап

1. **Починить `targets`**: компактный кэшированный ответ (имена, алиасы,
   профиль, машина/online, провайдеры без моделей), обновление в фоне раз в
   N минут и «холодный» прогрев на старте плагина. Ожидаемо 0.03–0.1 с вместо
   12 с и ~5 КБ вместо 100 КБ.
2. **Добавить рабочую цель** в `bb-targets.yaml` (алиас «по работе» / «джира»)
   и снять в документации формулировку «рабочие проекты не обсуждаются».
3. **Инструменты чтения**: `bb_projects`, `bb_threads`, `bb_thread_read`,
   `bb_task_status`, `bb_task_result` (поверх существующих
   `status`/`turn_result`).
4. **`bb_task_start` + `bb_task_tell`** поверх `spawn`/`send` с двухшаговым
   подтверждением (уже есть `prepare`/`confirm`).
5. **Доставка итога в Telegram**: расширить `updates` (или добавить
   `task_updates`) — завершённые ходы тредов, созданных плагином, — и
   опубликовать их через существующий Telegram-клиент mcp-gateway (у него уже
   есть фиксированный получатель и `infra_send_report`). Голосом итог читает
   уже работающий poller `/v1/voice/updates`.

Откат: инструменты добавляются отдельными группами, плагин и мост уже
существуют; откат — выключить группу `bb.*` в `MCP_GROUPS` и снять цели из
`bb-targets.yaml`. Ничего в Hermes заменить не нужно.

## Риски

- **Стриминг для TTS.** У bb есть потоковые события
  (`item/agentMessage/delta`), но текущий `voice-proxy` буферизует ответ
  (в замерах первый токен = полный ответ). Если понадобится говорить раньше,
  нужен стриминговый путь прокси → HA; сегодня это не требуется для команды
  «запусти».
- **Параллельность.** `threads.send` в занятый тред стеерит/ставит в очередь;
  два спутника (станция и телефон) могут прийти одновременно — нужен явный
  `mode` и `workerLimit` (сейчас 2).
- **Рестарты.** Сервер bb в CT: его перезапуск обрывает активные ходы; ACP- и
  CLI-провайдеры это переживают (тред остаётся, ход помечается failed),
  Hermes-ACP — тоже, но с потерей незавершённого хода. Мост (`bb-dispatch`) —
  stateless, переживает рестарт bb.
- **История и память.** Треды bb живут долго и требуют компакции — плагин уже
  сжимает диспетчерский тред ночью и по порогу контекста. Для рабочих тредов
  компакция — обычная, через bb.
- **Telegram.** Сейчас Telegram — канал самого Hermes (long polling в поде).
  Итог задачи должен приходить от того же бота; источник — mcp-gateway, чтобы
  не заводить второй канал и второй токен.
- **Окружение и файлы.** `spawn` использует `project-default`, то есть
  **рабочий checkout владельца**, а не worktree. Для голосовых задач это
  опаснее, чем кажется: агент пишет прямо в рабочее дерево. Нужен режим
  `worktree` для `bb_task_start`.
- **Приватность рабочего проекта.** Сейчас личный голосовой канал намеренно
  не знает о рабочих проектах. Разрешение «по работе» — осознанное решение
  владельца, оно должно быть явным и отражено в промпте и в allowlist.
- **Секрет в конфиге проекта.** В `bb project list --json` у рабочего проекта
  `gitRemoteUrl` содержит GitHub-токен в открытом виде (`ghp_…`). Это не
  относится к спросу напрямую, но любой инструмент, отдающий проекты голосу
  или в Telegram, обязан вырезать URL и не логировать его. Токен стоит
  перевыпустить и убрать из remote.
- **Версии.** bb server 0.48.1, CLI 0.50.1 — расхождение уже есть; контракт
  плагина (`contract/params.json`) надо держать совместимым с обеими.

## Приложение: как воспроизвести замеры

```bash
# 1. Hermes api_server (в поде, ключ из окружения контейнера)
mise run kubectl -- -n home-assistant exec -i deploy/hermes -c gateway -- \
  env N=5 /opt/venv/bin/python - < hermes-bench.py

# 2. Тот же скрипт через voice-proxy (URL=http://127.0.0.1:8643/v1/chat/completions)
# 3. bb: тред acp-opencode + gpt-5.6-luna, затем «tell → wait → output»
# 4. MCP-инструменты шлюза (bb_status, prepare/confirm)
mise run kubectl -- -n home-assistant exec -i deploy/hermes -c gateway -- \
  /opt/venv/bin/python - < mcp-bb-bench.py

# 5. Методы плагина напрямую (на CT bb; секреты читаются файлами, не печатаются)
pct exec 103 -- bash -s < dispatch-bench.sh
```

Замеры выполнены на bb 0.48.1; после исправления `targets` их нужно повторить.
