# GIT — ветки, pull request и выкладка

Как изменения попадают в `develop` и домой. Правила для агентов — `AGENTS.md`;
CI и маршрутизация юнитов — `TESTING.md`; деплой сервисов —
`projects/home/kubernetes/scheduler/README.md`.

## Ветки

| Ветка | Назначение | Публикуется |
|---|---|---|
| `develop` | основная, единственная долгоживущая; из неё деплоится дом | только через PR |
| `<type>/<name>` | рабочая ветка одного изменения | да, для PR |
| архивные refs, теги | локальные | никогда |

`<type>`: `feat`, `fix`, `chore`, `docs`, `ci`, `refactor`, `test`, `perf`;
`<name>` — строчные буквы, цифры, `.`, `_`, `-` (например `fix/deploy-digest`).

## Поток

```text
git fetch origin
git switch -c fix/<name> origin/develop     # или git worktree add … для параллельной работы
…правки, проверки, коммиты…
git push -u origin fix/<name>               # pre-push guard
gh pr create --base develop --fill          # PR в develop
# CI: ci-ok зелёный → mise run pr:merge <N> → ветка удаляется
# push в develop = merge PR → deploy-home выкатывает затронутые юниты
#   и job warm-caches прогревает общие кэши для следующих PR
```

- Одно логическое изменение — одна ветка и один PR. Мелкие PR проще
  проверять и откатывать.
- Заголовок PR становится сообщением squash-коммита: повелительное
  наклонение, по-английски, как в истории (`Add …`, `Fix …`).
- Описание PR: что и зачем, какие проверки выполнены, влияние на live
  (деплой, режимы, устройства). Секреты, реальные адреса и логи не вставлять.
- Долго живущий PR перед merge обновить от `develop` (rebase или merge в
  ветку) и дождаться нового `ci-ok`: после merge код сразу уходит в деплой.
  `mise run pr:merge <N>` делает это сам (см. «Merge»).
- После merge ветку не переиспользовать; следующая работа — новая ветка от
  свежего `origin/develop`.

## Merge

Merge в `develop` — только `mise run pr:merge <N>` (`platform/ci/safe-merge.mjs`,
тесты — `safe-merge.test.mjs`). Скрипт:

- требует OPEN PR в `develop` и полный head; конфликтующий PR — ошибка;
- сравнивает head с текущим `origin/develop`: если база устарела, по
  умолчанию вливает `develop` в ветку (`gh pr update-branch`) и ждёт новый
  head; конфликт при обновлении — ошибка без merge. Обновление ветки — это
  новый полный прогон CI (15–30 минут и раннеры), поэтому оно пропускается,
  когда merge безопасен и без него:
  - на текущем head зелёный `ci-ok`;
  - GitHub считает PR `MERGEABLE` (без конфликтов), а не `UNKNOWN`;
  - файлы PR (`merge-base..head`) и файлы новых коммитов `develop`
    (`merge-base..develop`) не пересекаются, включая старые имена переименованных
    файлов;
  - новые коммиты `develop` не трогают CI-глобальные пути: `.github/**`,
    `platform/ci/**`, `.bazelrc`, `.bazelversion`, `MODULE.bazel*`,
    `platform/android/android.bazelrc`, `mise.toml`, `Cargo.lock`,
    `**/maven_install.json`, `package-lock.json`, `pnpm-lock.yaml`,
    `platform/bazel/**` (константа `CI_GLOBAL_PATHS` в скрипте, покрыта тестом).
  Тогда скрипт печатает `develop +N commit(s), disjoint from PR files and no
  CI-global paths → merging on green ci-ok at <sha> without refresh` и мержит
  без `update-branch`: squash-tree отличается от проверенного tree только
  чужими по файлам коммитами `develop`, которые сами прошли CI. Если `ci-ok`
  ещё идёт, скрипт дожидается его, а не выбрасывает прогон. `--always-refresh`
  возвращает старое поведение — обновлять ветку при любом отставании;
- после обновления ждёт, пока compare для нового head догонит его (до ~60 с):
  GitHub несколько секунд отдаёт старый `behind_by`. Повторный `update-branch`
  не вызывается, пока `develop` действительно не получил новый коммит (sha
  сверяется через `git/ref/heads/develop`); счётчики обновлений ветки и
  реальных сдвигов `develop` независимы;
- ждёт зелёный `ci-ok` на этом head (check-runs API, `--timeout <min>`,
  по умолчанию 90 минут); красный или недождавшийся `ci-ok` не мержится;
- перед merge повторно проверяет, что `develop` не ушёл, и при необходимости
  повторяет обновление или заново проверяет безопасный merge без обновления
  (до трёх обновлений ветки);
- мержит `gh pr merge <N> --squash --admin --delete-branch
  --match-head-commit <head>`: если head сдвинулся между проверкой и merge,
  GitHub отказывает вместо merge непроверенного tree;
- печатает merge-sha и ссылку на запуск `deploy-home` (или подсказку, если
  запуск ещё не появился).

Почему не `gh pr merge` вручную: `ci-ok` проверяет tree PR, а squash-merge на
уехавший `develop` даёт tree, которого CI не видел, и `deploy-home`
fail-closed отказывает затронутым юнитам (PR #218 после #217). Рулсет не
strict, поэтому эту гонку закрывает только проверка базы непосредственно перед
merge. Проверка пересечения файлов не отменяет правило, а ослабляет его ровно
настолько: если `develop` и PR меняют разные файлы и не трогают CI-обвязку,
результат squash-merge — это tree PR плюс уже проверенные на `develop` файлы.
`--dry-run` показывает план без изменений, `--no-update` только
проверяет: устаревший head — ошибка, merge не выполняется, `--always-refresh`
отключает merge без обновления. Токен — обычный `gh`; `GH_TOKEN` учитывается и
не печатается.

## Защита на GitHub

Ruleset ветки по умолчанию (`develop`):

- прямой push, удаление и force-push запрещены; история линейная;
- merge только squash, только через PR;
- обязательная проверка `ci-ok` (итог CI, публикуется GitHub Actions);
- администратор может обойти правила только при merge PR — осознанным
  действием в интерфейсе. Мержить с красным `ci-ok` не нужно: исправить и
  дождаться зелёного.

## Локальная защита

`core.hooksPath=.githooks`, `pre-push`:

- разрешён только push текущей рабочей ветки `<type>/<name>` в одноимённую
  удалённую; `develop`, архивные refs и теги заблокированы;
- удаление веток через push заблокировано (ветки удаляет GitHub после merge);
- рабочее дерево чистое, Gitleaks по исходящим коммитам без находок,
  `platform/quality/audit_repository.mjs` без замечаний.

Не обходить guard (`--no-verify`, смена `hooksPath`, mirror push). Если в
основном checkout есть чужие незакоммиченные изменения, публиковать из
отдельного `git worktree` той же ветки.

## Учётная запись для push

Push и PR выполняются от аккаунта владельца репозитория. Если на машине
несколько GitHub-аккаунтов (например рабочий SSH-ключ), для этого
репозитория использовать HTTPS и `gh` как credential helper со своим
профилем, а не глобальный SSH-ключ:

```bash
git -c credential.helper= \
  -c 'credential.helper=!gh auth git-credential' \
  push https://github.com/<owner>/<repo>.git <type>/<name>
```

## Выкладка и откат

- Деплой — `.github/workflows/deploy-home.yml` на push в `develop`: только
  затронутые деплоимые юниты, параллельно, образы GHCR по digest.
- Режимы исполнения (`execute`, `shadow`, `control-*`) — только ручной
  запуск workflow с выбором режима.
- Неудачный деплой откатывает только то, что сам применил. Откат изменения
  целиком — новый PR с `git revert <squash-commit>`; историю `develop` не
  переписывать.

## Версии и публикация артефактов

- Native-юнит с `native.publish_when` (Pulsar, Windows logon provider)
  собирается и проверяется PR CI на любое изменение своих путей и общих
  входов (Cargo workspace/lock, используемые `packages/rust/*`, тулчейны,
  `MODULE.bazel`) и публикует артефакт как `tree-<hash>` с provenance.
  Релизные теги `VERSION` ставятся только при изменении файла версии:
  изменение исходников без бампа `VERSION` — проверка, а не релиз. На push
  `deploy-home` только продвигает опубликованный `tree-<hash>`; если его нет
  или provenance не сходится, job падает — деплой ничего не собирает.
- Релиз — осознанный бамп `VERSION`; тег версии в GHCR неизменяем по
  содержимому, поэтому повторная публикация того же артефакта — no-op, а
  другого содержимого под тем же тегом — ошибка.

## Агенты

- Исполнитель работает в рабочей ветке или отдельном worktree, может
  коммитить в неё, но не пушит и не открывает PR.
- Primary проверяет diff и результаты проверок, публикует ветку, открывает
  PR, дожидается `ci-ok`, мержит и проверяет деплой.
- Вложенные upstream-репозитории в `resources/` живут по своим правилам из
  `AGENTS.md`; их ветки и remote этот поток не трогает.
