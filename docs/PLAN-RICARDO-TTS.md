Предлагаемые новые пути в репозитории, пока не созданные реализацией:

Для первого Silero-пилота изучить `staastas/wyoming-silero`, зафиксировать commit и собрать образ или выбрать проверенный digest. Не использовать движущийся `latest` в постоянной установке. Проверить реальные параметры `apply_tts`, модельный каталог и поддержку конкретного speaker. В официальном `models.yml` выбранные CIS-модели лежат под языковым ключом `ru`; не копировать предположение `multi` без проверки.

Ниже — **эскиз параметров**, который нужно проверить на закреплённой версии обёртки; digest подставляется после сборки/проверки:

```yaml
services:
  ricardo-tts:
    image: ${RICARDO_TTS_IMAGE:?set pinned image digest}
    restart: unless-stopped
    ports:
      - "127.0.0.1:10209:10200"
    environment:
      SILERO_LANGUAGE: ru
      SILERO_MODEL: v5_6_ru
      SILERO_SPEAKER: eugene
      SILERO_SAMPLE_RATE: "48000"
      WYOMING_PORT: "10200"
    volumes:
      - ./data/ricardo-tts:/app/silero/model
```

HA в текущем Compose работает в host network, поэтому ему доступен localhost:10209. Piper :10200 продолжает работать отдельно. Порт 10209 — предложение; перед запуском проверить занятость. mDNS не обязателен: интеграцию можно добавить вручную. При переносе HA в bridge-сеть loopback-схема потребует изменения.

Сервис загружает модель один раз, делает прогрев до readiness, держит один inference worker. Начальные варианты CPU threads — 2 и 4; сравнить под нагрузкой, не занимать все потоки i7 по умолчанию. Ограничения RAM и CPU ставить после измерений, оставляя запас STT/HA/музыке.

Проверить холодный запуск без интернета после наполнения кеша. Если обёртка всё равно требует обновлять `models.yml`, закрепить локальный каталог или исправить стартовый путь. Наличие cached weights само по себе не доказывает offline readiness.

## 4. Контракт и подготовка текста

Для собственного адаптера обязательны Wyoming `Describe/Info`, корректный voice discovery, `Synthesize`, `AudioStart` → PCM `AudioChunk` → `AudioStop`, явный `Error` при отказе. Формат первого релиза — mono PCM signed 16-bit little-endian; native sample rate либо один явно заданный качественный resample. Stereo MOSS свести в mono с контролем уровня.

Не объявлять streaming input, пока не реализованы и проверены соответствующие start/chunk/stop и stopped события. Большая нарезка одного готового WAV — транспортная пакетизация, а не потоковое вычисление модели.

Frontend должен обслуживать **и local intents, и Hermes, и вызовы tts.speak**. Если поставить его только в `hermes-voice-proxy`, таймеры и будильник его обойдут.

Порядок обработки:

1. Unicode и пробелы, удаление URL/служебной разметки на границе TTS; корректная обработка пустого результата.
2. Детерминированная нормализация времени, единиц, чисел и сокращений. Для сложных дат/склонений использовать проверенную библиотеку и fixtures, не бесконечный набор regex. Где HA уже дал правильные слова, не менять их.
3. Словарь произношения проекта: «Рикардо», Spotify, Music Assistant, GigaAM и нужные исполнители. Сохранять отдельный display text; не портить текст истории.
4. Backend-specific ударения: CIS — RUAccent и адаптация его разметки к синтаксису `+` модели; Kokoro — штатный ru_g2p/RUAccent; RU Silero — встроенный механизм с проверенными overrides. Не отправлять Silero `+` в Qwen/MOSS без подтверждения поддержки.
5. Разбиение слишком длинного текста на естественные предложения без потери последней части. Лимит из voice prompt — предпочтение, а не гарантированная граница входа TTS.

Для CIS проверять **подготовленный** текст, а не пытаться включить отсутствующий auto-stress параметром. Для имени закрепить произношение «Рика́рдо» после прослушивания.

Кеш сервиса нужен только при реальной необходимости сверх HA. Ключ: text после frontend + model hash + speaker/reference hash + frontend revision + rate + synthesis options. Профиль должен иметь revision, иначе после смены тембра старые ответы могут звучать из HA-кеша. При пилоте отключить кеш; после принятия очистить/версионировать его поддерживаемым способом.

## 6. Обработать будильник и отказ TTS

В `projects/home-assistant/ha-voice/scripts.yaml`, блок `alarm_announce`, есть отдельная ссылка на `tts.piper`. После приёмки основного TTS её нужно либо заменить выбранным entity, либо направить в отдельный speech script. **Не менять** `media_player.iandeks_stantsiia_midi_media_player`, chime, volume ramp, stop/snooze и восстановление Spotify.

Статическую фразу «Доброе утро. Пора вставать.» предпочтительно заранее отрендерить выбранным голосом в локальный WAV. Тогда звонок не зависит от загрузки нейросети в момент пробуждения. Chime обязан сработать даже при недоступности speech-сервиса. Для динамического времени/даты использовать новый TTS с резервом.

Просто оставить Piper-контейнер включённым **не означает автоматический fallback** Assist. Первый релиз может иметь документированный ручной откат. Если требуется автоматический резерв, это отдельная функция: Wyoming-router на границе синтеза с primary и Piper, либо полноценный эквивалентный адаптер. Один HA-script для `tts.speak` не перехватит весь Assist.

Политика router: при отказе до первого отправленного аудио — ограниченный retry/fallback; после начала речи — не воспроизводить ту же фразу с начала вторым голосом. Если нужно гарантировать целостную реплику, буферизовать её перед отправкой и принять дополнительную задержку. Разорванный клиентский запрос отменяет/сбрасывает вывод; завершившийся старый job не должен зазвучать позже.

Piper можно оставить с Irina для абсолютно точного отката или отдельно выбрать мужской голос для более согласованного резерва. Смена резервного голоса тоже требует прослушивания. Отключённый интернет, остановленный Hermes и падение нового TTS тестируются как разные отказы.

## 7. Приёмка

| Проверка | Порог/ожидаемый результат |
|---|---|
| Слышимое начало после готового текста HA | warm p95 ≤1.5 с для ответов до 180 знаков; ≤0.8 с — желательная цель |
| Потоковый backend, если используется | TTFA p95 ≤0.5 с, RTF p95 ≤0.5; не подменять ими задержку колонки |
| Числа, время, смысл | Нет критических подмен на основном корпусе |
| Имя и тембр | «Рикардо» произносится стабильно, голос не меняется между репликами |
| 100 запросов под фоновой нагрузкой | Нет OOM, потерянных концов, повторного воспроизведения; не ухудшаются STT и музыка |
| Отмена / «стоп» / новый запрос | Нет запоздалой речи от прежнего запроса |
| Модель недоступна | Явная ошибка или проверенный fallback; нет бесконечного responding |
| Сеть отключена | Локальные команды и локальный TTS работают после рестарта сервиса |
| Будильник | chime, речь, stop/snooze, source/volume restore и resume музыки работают |
| Перезапуск HA/сервера | Сервис прогревается и корректно определяется; pipeline восстановлен |

Пороги — проектные цели, не обещание текущих моделей. Если текущий Piper сам превышает порог из-за аудиотракта, сначала разложить задержку по этапам. Не пытаться компенсировать проблему TTS изменением 25-секундного watchdog.

Основной корпус: 36 реплик, по 3 повтора для двух финалистов; cold start отдельно 5 раз. Собирать p50/p95/max, RAM RSS/контейнерный peak, загрузку CPU, время frontend, полный synth time, first PCM и начало звука на станции. 100-запросный прогон дополнительно. ASR round-trip дополняет ручной разбор ошибок, а не заменяет его.

Сначала MOSS ONNX: 2–3 референса одного выбранного мужского образа, один набор фраз, фиксированные настройки; проверить нейтральный ответ, вопрос и ошибку. ## 10. Оценка работ

Оценка для одного разработчика при рабочем доступе и доступных весах:

- Доступ, baseline, новый набор прослушивания: 0.5–1 рабочего дня.
- Silero Wyoming, закрепление версий, HA pilot: 0.5–1 дня.
- Frontend, будильник, meaningful tests и отказоустойчивость: 1–2 дня; автоматический router может добавить 1–2 дня.
- Акустическая приёмка и переключение: 0.5–1 дня плюс сутки наблюдения.
- MOSS/Kokoro с собственной обёрткой: ещё 1–3 дня на выбранный путь; Qwen — отдельный spike 1–3 дня без гарантии прохождения CPU-порогов.

Разумный объём первого релиза — **примерно 3–5 рабочих дней** без обязательного автоматического router и без клонирования. Доступ, выбор понравившегося тембра и измерения на lab-host — реальные зависимости, а не формальности.
