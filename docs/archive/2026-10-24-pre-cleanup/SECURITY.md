# Безопасность и риски

## Юридическое / этическое

- Комплект использует **приватный ключ intermediate-CA eMudhra**, полученный
  из публичной утечки (eQuasar). Применять только к **своей** колонке в
  **своей** сети.
- Не публиковать `secrets/`, `leaf.key`, `ca.key`, архивы и логи с токенами.
- Не направлять на стенд чужие устройства и не выставлять порты в интернет.
- Прошивка обновлена на официальную версию; модифицированных образов нет.

## Сеть

| Порт | Где | Доступ | Риск |
|---|---|---|---|
| `53/udp` | Mac | вся LAN (через роутер) | при падении DNS ломается резолв во всей сети |
| `80/443` | Mac | LAN | MITM-стенд, сертификаты eMudhra |
| `31116` | Mac | LAN | API эмулятора (push/config) без авторизации |
| `22` | колонка | LAN | root по паролю (см. `secrets/CREDENTIALS.md`) |
| `5555` | колонка | LAN | ADB root **без пароля** |

- Роутер форвардит DNS на Mac. Если Mac уйдёт в сон/выключится — вернуть
  Static DNS на `192.0.2.1`; на карантин это уже не влияет (есть egress-guard).
- `5555` и `22` не пробрасывать наружу, не держать в гостевой сети.
- `31116` — API push/config без auth; любой в LAN может отправить директиву.
  Закрыть bind `127.0.0.1`/auth — P0 в `docs/PENDING.md`.
- Пароль SSH слабый; заменить/ключи — в `docs/PENDING.md`.

## Egress-guard

- На станции стоит `EGRESS_GUARD`: разрешены loopback, private LAN (`10/8`,
  `172.16/12`, `192.168/16`, `100.64/10`), link-local/multicast, DHCP и Google
  NTP; остальной IPv4/IPv6 `OUTPUT` — `DROP`.
- Яндекс блокируется по IP, а не по DNS: отключение DNS на роутере/Mac не
  ослабляет карантин. ADB/SSH и доступ из LAN сохраняются.
- Доверие private LAN: устройство в такой сети может быть прокси. Для строгого
  режима сузить allowlist до Mac + конкретного admin-IP.
- DPP QR/DER-ключ (`secrets/dpp`) дают возможность провижининга; не публиковать.
  Sound-код содержит Wi-Fi-пароль в звуке; проигрывать только рядом.
- Google NTP — единственное WAN-исключение; при необходимости убрать.
- Откат: `/data/quasar/egress-guard-off.sh`; он **не** снимает Yandex-блок/OTA.
- Guard живёт в `/data`; factory reset/wipe `/data` его удалит.

## Секреты

`secrets/` (chmod 700), внутри:
- `dpp/` — DER-ключ, bootstrap URI и QR (доступ к Wi-Fi-провижинингу);
- `certs/*.key` — приватные ключи eMudhra/leaf;
- `emudhra-ca.key` — ключ intermediate-CA (самый чувствительный);
- `CREDENTIALS.md` — пароли/доступы.

Не коммитить, не синхронизировать в облако без шифрования, не пересылать.

## Логи

- `alice-mitm-bootstrap/logs/requests.jsonl` может содержать OAuth-токены,
  device_id, пути запросов.
- Логи стека (`docker compose logs`) содержат трафик колонки.
- Не публиковать; при передаче — вычищать.

## Обновления

- OTA-запрет установлен (23.10.2026): `updatesd` вырезан, `ota_script.pub`
  подменён, `device_ota_update.sh` — no-op; s3/cdn на прокси → `403`.
- После `--ota-off` обновление возможно только после снятия запрета.
- **Factory reset/recovery на Midi не проверен.** Проверенного factory-образа
  `cucumber` нет; в `artifacts/firmware/` лежит `yandexmidi` (Station 2), не Midi.
  Сброс сносит `/data` (keeper, SSH, пароль, OTA/telemetry-скрипты) и может
  вернуть стоковое поведение, но **не гарантирует** снятие серверного лока/
  `stolen` и не является проверенным unbrick. Raw-дампа recovery нет.

## Целостность

- Корень `/` — `ro`, изменения (SSH, CA, OTA-файлы) требуют `remount,rw`.
- `verifiedbootstate=green`; модификация system пока tolerated (CA/ADB
  работают), но не злоупотреблять.
- Перед изменениями делать бэкап оригиналов в `/data/opt/backup`.

## Что не делать

- Не запускать `rollback.sh` от Mini 2 на Миди: там MTD/UBI и другие
  разделы (`mtd2/mtd3/mtd6`), у Миди eMMC/ext4. Можно окирпичить.
- Не применять `yandex-micro-kit.sh` без сверки путей маркеров: в нём
  `/data/quasar/activate_adb_*`, а на старой прошивке было
  `/data/quasar_activate_*`; сейчас совпадает, но проверять.
- Не менять `ota_script.pub` до того, как убедился, что обновление больше
  не нужно.
