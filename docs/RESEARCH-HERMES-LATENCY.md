# Задержка голосового ответа Hermes: анализ и план ускорения

Дата: 2026-10-27. Анализ исходников и сохранённого состояния; без изменения конфигурации и устройства.

Позднее low reasoning и streaming внедрены по запросу пользователя: [результаты и откат](DEPLOY-HERMES-STREAMING.md). Ниже сохранён исходный анализ до внедрения.

## Вывод

Первая кандидатура для небольшого эксперимента — явно снизить reasoning в голосовом профиле. Главное подтверждённое архитектурное ограничение — ожидание полного ответа: HA streaming отключён, а voice_proxy дополнительно принудительно выставляет `stream=false` и целиком читает upstream response. Для сокращения времени до первых слов нужен поток через всю цепочку до воспроизведения, с безопасной очисткой текста по завершённым фрагментам.

Нельзя пока назвать главный источник секунд или обещать конкретное ускорение: в доступных отчётах нет разбивки задержки. SSH на Ethernet `.26` завершился timeout; Wi-Fi `.25` доступен, но текущая SSH-аутентификация не прошла. Полная runtime-конфигурация, логи текущих вызовов и фактические сетевые параметры не проверены. Секреты для исследования не извлекались; live-вопросы модели не запускались.

## Что сейчас работает

Канонический источник — `STATE.md`, а не более старые схемы в `ARCHITECTURE.md`: там ещё встречаются «Алиса» и Irina.

```text
Рикардо / microWakeWord на станции
  → Pulsar: VQE, pre-roll, ESPHome audio
  → HA: окончание речи / VAD
  → GigaAM v3 CTC int8 на CPU неттопа
  → local intents (дом, громкость, таймеры, будильник, музыка)
  → если локально не обработано: conversation.hermes_agent / llama_cpp
  → voice_proxy :8643 (stream=false)
  → Hermes v0.22.5 :8642
  → ChatGPT/Codex OAuth → gpt-5.6-luna
  → при необходимости native web search или разрешённые HA MCP tools
  → полный ответ → очистка URL/Markdown → HA
  → Piper / Puriso → HTTP audio → Pulsar / GStreamer → первые слышимые слова
```

Hermes — агент-оркестратор; модель выполняется удалённо. Покупка более мощного неттопа сама по себе не ускоряет облачное reasoning и поиск. Текущий i7-12650H обслуживает локальные STT/TTS; насыщение CPU ещё не измерено.

## Подтверждённые ограничения и гипотезы

| Участок | Что известно | Следствие |
|---|---|---|
| Voice proxy | `do_POST` принудительно отключает stream; `_upstream` делает `resp.read()` | Первый текст доходит до HA только после полного ответа |
| HA conversation | Сохранённый профиль использует `streaming=false`; upstream HA 2026.10.4 умеет читать stream | Одной смены настройки HA недостаточно: прокси надо менять согласованно |
| Pulsar | `INTENT_PROGRESS` с `tts_start_streaming=1` вызывает `play_tts()` | В спутнике уже есть путь раннего запуска; совместимость надо проверить на установленной версии |
| Reasoning | В версионируемом Hermes fragment нет `agent.reasoning_effort` | Реальный уровень неизвестен; документация Hermes указывает medium по умолчанию |
| Краткость | HA prompt просит 1–2 предложения и до 180 символов | Это ограничение в инструкции, а не гарантированный предел вычислений/токенов |
| Web | Используется `openai-native` | Поиск встроен в provider transport; нельзя автоматически считать его отдельным дополнительным клиентским LLM-вызовом |
| MCP | Разрешены 15 музыкальных/домашних tools | Возможны дополнительные agent turns и большие результаты, но их частота и длительность неизвестны |
| STT | GigaAM int8, warmup включён в compose | Уже выбран разумный локальный путь; заменять его до измерения нет оснований |
| VAD | В upstream HA 2026.10.4 базовое silence_seconds=0.7; чувствительность настраивается | Есть неизбежное ожидание окончания речи; это не подтверждённая настройка вашей станции |
| Таймауты | Proxy 180 с, MCP connect 20 с / operation 90 с | Верхние пределы ожидания при проблеме, а не фиксированная добавка к каждому запросу |

Источники в проекте: `projects/home-assistant/hermes/voice_proxy.py`, `config.fragment.yaml`, `voice_prompt.txt`, `README.md`; `projects/home-assistant/stack/docker-compose.yml`; `projects/station/upstream/pulsar/satellite/src/controller.cpp`.

Промпт Hermes fragment ещё говорит 1–3 предложения, актуальный `voice_prompt.txt` — 1–2/180 символов. В документации говорится об обновлении runtime voice personality; это надо сверить, а не считать fragment полным runtime-конфигом.

## Приоритет 0: получить измерения, которые объяснят задержку

Основная метрика — время от конца речи пользователя до первого слышимого звука ответа. Отдельно измерять длительность полного ответа и готовность к следующему запросу. `run-end`, `tts-end` и состояние `responding` не заменяют акустическое измерение.

На один запрос нужны коррелированные отметки:

1. Последний речевой фрейм, VAD end, STT end.
2. Local-intent fallback / начало Hermes, получение запроса proxy и Hermes.
3. Начало provider request; первый текстовый delta; завершение ответа. Keepalive, reasoning и сообщение «ищу» не считать первым содержательным ответом.
4. Начало/конец каждого MCP tool и поиска, число модельных итераций, повторы/429/auth refresh, входные/выходные токены и reasoning usage, если доступны.
5. Начало TTS, получение первых аудиобайт, начало воспроизведения на станции.

Для одного хоста использовать monotonic clock. Между HA и станцией — синхронизацию/корреляцию с учётом погрешности. Не хранить аудио, токены и полные тексты в постоянном диагностическом журнале; для анализа достаточно идентификаторов и времён.

Сравнивать четыре класса: локальная команда; обычный вопрос без tools; актуальный вопрос с web; музыкальный запрос с MCP. Отдельно первый запрос после простоя, повторные независимые запросы и длинный диалог. Начать с 5–10 повторов для разведки и медианы/диапазона; для устойчивого p95 нужен более крупный набор. Кешированные ответы/повторный TTS не выдавать за новый inference.

Изоляция по уровням: прямой Hermes → proxy → HA text pipeline → voice. Для text pipeline исключить фактическое воспроизведение; полный voice-тест выполнять отдельно, сохраняя duck/resume, mute и будильник.

## Приоритет 1: снизить reasoning, сохранив текущую модель

Предложение для эксперимента, не применённая настройка:

```yaml
agent:
  reasoning_effort: low
```

Сравнить с текущим effective level. Затем отдельно проверить `none`, если установленная модель/маршрут принимает его без fallback/retry. `low` — более осторожная первая ступень для ASR-искажений и выбора tools. Пустой/пропущенный параметр не считать выключенным reasoning.

Снижать вычисления только голосового профиля: общий Hermes может использоваться другими клиентами. Проверить, что параметр реально доходит до провайдера и не перекрыт model/session/request override. Оценить правильность ответов, восстановление искажённых слов, выбор музыки и отсутствие лишнего поиска.

Не путать 180 символов с token budget. Жёсткий низкий `max_tokens` без проверки реализации Hermes может не ограничить модель или оборвать ответ/рассуждение. Поле входного OpenAI-compatible запроса не гарантирует, что внутренний agent применит его как ожидается.

## Приоритет 2: потоковая цепочка до первых слов

Предлагаемый путь:

```text
Hermes text deltas
  → SSE proxy с очисткой законченных текстовых фрагментов
  → HA llama_cpp streaming / chat log
  → ранний TTS и выдача аудиобайт
  → существующий Pulsar INTENT_PROGRESS → play_tts
```

Нужно проверить не только SSE, но и установленный Piper/Wyoming, выдачу аудио HA, формат и буферизацию GStreamer. Потоковый текст без раннего аудио не решает задачу пользователя.

Очистка по отдельным токенам некорректна: URL, Markdown-ссылка и цитата пересекают границы chunks. Нужен небольшой буфер, обработка законченных фраз/предложений, завершение хвоста и фильтрация служебных событий. Нельзя озвучивать reasoning, tool progress, внутренние имена и преждевременное «включил» до успеха действия. Нужны отмена при barge-in, защита от позднего ответа и сохранение текущего duck/resume.

Upstream Hermes имеет stream delta callbacks, но наличие SSE не доказывает ранний выход именно финального ответа во всех agent/tool-сценариях. Это измерить отдельно. Streaming сокращает ожидание начала ответа; не обязательно сокращает общее время вычислений. При очень коротком ответе выигрыш от генерации может быть скромнее, чем от снижения reasoning.

## Приоритет 3: уменьшить лишнюю агентную работу

- Измерить фактический system prompt, историю, tool schemas и результаты MCP. HA prompt добавляется поверх базового Hermes prompt; короткий видимый voice prompt не означает короткий общий контекст.
- У Hermes теперь полный HA/MA MCP surface (57+86 tools); это осознанно. Для latency измерять tool schemas, память, skills, компрессию истории и init/discovery MCP; при необходимости оптимизировать схему, не сужая доступ без запроса. Локальные intents остаются быстрым путём.
- У музыкального поиска отдавать компактный top-N с необходимыми полями, а не большие каталоги. Сохранять ссылки на реальные результаты и правило «не выдумывать URI».
- Дом, громкость, таймеры и будильник оставлять в local intents. Расширять их по реальным промахам STT. Здесь уже выведены из Hermes next/previous/resume — продолжать по тому же принципу.
- Повторяемые актуальные вопросы вроде погоды можно обслуживать отдельным HA intent/интеграцией с актуальными данными. Это устраняет поиск и агентное решение, но добавляет интеграцию и требует проверки источника/свежести.
- Не отключать web целиком: тогда цены, новости и погода ускорятся за счёт достоверности. Для постоянных знаний проверять отсутствие ненужного поиска.

## Приоритет 4: сравнить модели и упрощённый путь

Если после настройки reasoning и streaming обычные вопросы всё ещё медленные, провести одинаковый набор через текущую модель и доступные быстрые альтернативы. В документации проекта есть уже полученные HTTP 400 для нескольких моделей; нельзя назначать новую только по каталогу или названию. Проверять доступность именно через текущий account/provider, затем русский язык, tools, ASR-искажения и задержку. Смена модели/провайдера может менять стоимость и условия доступа.

Более серьёзный вариант — простой voice backend для вопросов без tools и Hermes для поиска/действий. Упрощение может убрать базовый agent prompt и инициализацию, но его польза должна подтверждаться сравнением с текущим Hermes. Второй облачный LLM-классификатор перед каждым запросом добавит задержку; сначала использовать явные правила и локальные intents. Сохранять диалоговый контекст между маршрутами.

Локальная небольшая модель на i7 без подтверждённого GPU — отдельный эксперимент. Она убирает зависимость от WAN, но CPU prefill/генерация и качество русского/tool calling могут оказаться хуже. Покупку GPU, замену STT и переход на speech-to-speech сейчас не обосновывают измерения.

## Дополнительные проверки

- VAD: уменьшать ожидание только после замера и проверки естественных пауз. Вероятный масштаб выигрыша — доли секунды, если исходная настройка близка к штатной. Не жертвовать концами команд и pre-roll.
- Wake arbitration в Pulsar имеет окно 250 мс; это до/вокруг начала запроса, а не объяснение долгого ожидания после конца вопроса. Оно не обязательно полностью добавляется к пользовательской метрике. Для одной колонки оптимизация второстепенна.
- Regex sanitizer сам по себе не похож на источник многосекундной работы на коротком тексте; проблема proxy — полная буферизация. Удаление proxy целиком вернёт чтение ссылок и Markdown.
- Для TTS измерять реальное получение/воспроизведение аудио. В Puriso deployment уже правильно отмечено, что быстрый `tts-end` может означать только выдачу ленивого/кешированного URL.
- Watchdog `responding` на 25 с и Pulsar processing watchdog — отдельная тема восстановления. Не трактовать их как обязательную паузу перед ответом. Проверить, не обрывает ли HA watchdog допустимый длинный ответ.
- Не выполнять повторные действия при retry и не продолжать заброшенный вопрос после новой активации. Таймауты улучшают предсказуемость отказа, а не скорость успешного inference.

## Рекомендуемая последовательность

1. Короткий baseline по этапам и сверка runtime-конфигурации.
2. Один эксперимент reasoning=low; при необходимости none; проверка качества.
3. Прототип сквозного streaming с сохранением sanitizer и ранним аудио.
4. Оптимизация выявленных tool/prompt/history расходов и локальных промахов.
5. Сравнение моделей/упрощённого backend только если остаточная задержка этого требует.

Ориентир для проектирования, не обещание измеренной производительности: обычный вопрос — первые содержательные слова примерно за 2–3 с после конца речи. Веб-запросы оценивать отдельным классом; короткий сигнал «ищу» улучшает обратную связь, но не заменяет сокращение времени до ответа.
