# contracttest

Общий раннер golden-фикстур внешних HTTP-контрактов Go-сервисов. Один и тот
же файл проигрывает Go-тест сейчас и будущая Rust-реализация: формат ниже
нормативный, менять его нужно вместе с раннерами обоих языков.

Пакет нужен, когда сервис переписывается на другой язык: фикстуры фиксируют
wire-поведение (методы, пути, статусы, значимые заголовки, тела), а не
внутреннее устройство.

## Файлы

`<пакет>/testdata/contract/<scenario>.json` рядом с тестируемым пакетом,
один файл на сценарий:

```json
{
  "name": "create_schedule_idempotency",
  "description": "почему сценарий важен и какие плейсхолдеры использованы",
  "steps": [
    {
      "request": {
        "method": "POST",
        "path": "/home.v1.SchedulerService/CreateSchedule",
        "headers": {"Authorization": "Bearer fake-token", "Content-Type": "application/json"},
        "body": {"label": "wake", "idempotencyKey": "k1"}
      },
      "capture": {"scheduleId": "schedule.id"},
      "captureHeaders": {"session": "Mcp-Session-Id"},
      "response": {
        "status": 200,
        "headers": {"Content-Type": "application/json"},
        "body": {"schedule": {"id": "{{scheduleId}}", "revision": "1"}}
      }
    }
  ]
}
```

Поля шага:

| Поле | Обязательно | Значение |
|---|---|---|
| `request.method` | да | HTTP-метод |
| `request.path` | да | путь; подставляются `{{name}}` |
| `request.headers` | нет | заголовки запроса дословно (после подстановки) |
| `request.body` | нет | JSON-значение или строка |
| `response.status` | да | ожидаемый HTTP-статус |
| `response.format` | нет | `sse` — тело является SSE-кадром `event: message\ndata: <json>\n\n`; байтово проверяется обрамление, `body` сравнивается с JSON-payload |
| `response.headers` | нет | только значимые заголовки; остальные игнорируются |
| `response.body` | нет | JSON-значение (структурное сравнение) или строка (побайтное) |
| `compare` | нет | режим сравнения тела: `exact` (по умолчанию) или `semantic`; можно задать на файле и переопределить на шаге |
| `capture` | нет | имя → путь в JSON-ответе (`schedule.id`, `events[0].id`) |
| `captureHeaders` | нет | имя → имя заголовка ответа |

## Сравнение

- `response.body` — JSON-объект/массив/число → структурное сравнение: порядок
  ключей не важен, лишние и недостающие ключи — ошибка.
- `response.body` — строка → побайтное сравнение (SSE, `ok\n`, текст).
- Тело ответа, которое не является JSON, в `-update` записывается строкой
  как есть.
- Числа в фикстуре декодируются как `float64`, в ответе — как `json.Number`;
  сравнение идёт по десятичному представлению.

### Семантический режим (`compare: semantic`)

Режим для кадров, которые генерирует MCP SDK: реализация на другом SDK или
другой версии протокола может добавить необязательные поля, не меняя смысл
контракта. В семантическом режиме:

- объекты сравниваются как **подмножества**: каждый ожидаемый ключ должен
  присутствовать и совпасть, лишние фактические ключи разрешены;
- массивы остаются **точными** (длина и порядок важны): список инструментов,
  алертов или сервисов — часть контракта;
- скаляры, числа и плейсхолдеры сравниваются так же, как в `exact`.

Так фиксируются имена инструментов, описания, свойства `inputSchema`,
аннотации `readOnlyHint`/`destructiveHint` и `speech`/`details`, но
Go-специфичные `ttlMs`, `cacheScope` или `idempotentHint: false` можно
опустить: они не входят в ожидаемое подмножество. Режим обязан одинаково
работать в обоих раннерах (`packages/go/contracttest` и
`packages/rust/home-contracttest`).

### SSE (`response.format: "sse"`)

Обрамление кадра проверяется побайтно: тело обязано начинаться ровно с
`event: message\ndata: ` и заканчиваться `\n\n`. Полезная нагрузка между ними
декодируется как JSON и сравнивается по правилам `compare` (`exact` или
`semantic`). В `-update` в фикстуру пишется именно JSON-payload, а обрамление
не сохраняется: оно нормативно и проверяется раннером.

## Подстановки и плейсхолдеры

- `{{name}}` в `path`, `headers`, `body` запроса и в ожидаемом `body`
  заменяется значением из `capture`/`captureHeaders`. Отсутствующее имя —
  ошибка теста.
- `<uuid>` в ожидаемом теле совпадает с любым каноническим UUID.
- `<base64-32>` совпадает с base64 любых 32 байт (nonce).
- `<any>` совпадает с любым непустым значением (в том числе числом).
- Значения, захваченные в `capture`, при `-update` записываются обратно как
  `{{name}}`, поэтому фикстуры остаются детерминированными.

## Недетерминизм и нормализация

Сервис обязан убрать недетерминизм инжекцией (фейковые часы, фиксированные
ключи). Если seam'а нет, сервис передаёт `WithNormalizer`: он получает уже
подставленные `{{name}}` и заменяет свои случайные значения на
`<uuid>`/`<base64-32>`/`<any>`; причина и плейсхолдер описываются в
`description`. `WithBeforeStep` получает имя сценария и номер шага, поэтому
позволяет двигать фейковые часы и выполнять tick движка между шагами
конкретного сценария.

## Запуск

```bash
# сравнение
go test ./solutions/<service>/... -run TestContractFixtures

# перезапись ответов (локальная разработка)
go test ./solutions/<service>/... -run TestContractFixtures -update
```

`Run(t, dir, newServer, opts...)` сам находит каталог в двух режимах: из
каталога пакета (`go test`) и от корня runfiles (Bazel). `dir` передаётся
репозиторий-относительным путём; дополнительно пробуется суффикс от
`testdata/`.

`newServer(t, scenario)` вызывается на каждый сценарий и возвращает готовый
`http.Handler` с фейковыми зависимостями; там же можно засеять состояние
(например, тест-вектор nonce и гранта), потому что имя сценария доступно.

## Обязательства Rust-раннера

Будущая реализация должна поддерживать те же `capture`, `captureHeaders`,
`{{name}}`, `<uuid>`, `<base64-32>`, `<any>`, структурное сравнение JSON и
побайтное сравнение строк, режимы `exact`/`semantic` и `response.format: "sse"`.
`-update` должен переписывать только `response`-половину фикстур, не меняя
запросы и описания.
